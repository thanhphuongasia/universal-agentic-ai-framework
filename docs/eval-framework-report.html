Tóm tắt 1 câu: với phần mềm truyền thống ta viết unit/IT test vì output cố định; với LLM output biến thiên nên không assert được — phải eval (chấm điểm theo tiêu chí). Mà eval cần expectation cho mỗi case; trong codebase lớn con người tự làm thì cực & dễ sai, nên có phase Golden Dataset dùng LLM mạnh sinh expectation → người chỉ duyệt → promote thành fixture cho eval dùng.

W WHY — Vì sao cần Eval framework?

Phần mềm truyền thống: unit test / IT là đủ

Code thường tất định (deterministic): cùng input → luôn cùng output. Nên test chỉ cần assertEquals(expected, actual). Pass/fail rõ ràng.

LLM: output biến thiên → assert "==" vô dụng

Cùng một input, LLM có thể trả lời khác nhau mỗi lần (nhiệt độ, sampling, đổi model, đổi prompt). Không thể so khớp tuyệt đối. Phải chấm theo tiêu chí mềm: đúng cấu trúc, chứa thông tin cần, vượt ngưỡng tương đồng, đúng op CRUD… → đó là việc của eval.

Bối cảnh codebase lớn

Với hàng trăm route / entity / field, việc tự tay tạo "đáp án đúng" cho từng field của từng entity là bất khả thi: con người dễ miss, mệt mỏi, sai sót, và không nhất quán. Không thể nhìn từng dòng code để dựng golden dataset thủ công.

Vì sao không "chờ production rồi xem"?

Chờ chạy thật rất chậm & rủi ro, và không so sánh công bằng được nhiều model / nhiều phiên bản prompt cùng lúc. Eval cho phép thử offline, lặp nhanh, so sánh A/B trước khi ship.

5 Khung 5W2H — nhìn nhanh toàn cảnh

What

Là cái gì

Hệ chạy bộ test case (input + expected) qua model/prompt, rồi chấm điểm & so sánh. Tổ chức theo System → Domain → Suite → Case / Prompt version / Run.

Why

Vì sao

LLM output biến thiên → unit test không đủ. Cần đo chất lượng & so sánh model / prompt version.

Who

Ai

Dev / prompt engineer chạy eval. Reviewer (người) duyệt Golden Dataset trong Oracle Review UI.

When

Khi nào

Trước khi đổi prompt/model, kiểm hồi quy, so sánh phiên bản — không chờ production.

Where

Ở đâu

Ryuu Eval: Suite → Case → Prompt version → Run. Expectation tạo ở Oracle Review (Golden Dataset). Fixture lưu file; case/run lưu Postgres.

How

Làm thế nào

Oracle Review sinh expectation (6 bước) → người duyệt → promote thành test_case trong DB → Run chấm điểm qua Scorer.

How much

Bao nhiêu / chi phí

Tự động hoá phần nặng (sinh expectation bằng LLM mạnh); người chỉ review cell low/medium → tiết kiệm công, giảm sai sót.

H HOW — Luồng Eval (dùng expectation để chấm)

Mỗi case có input và expected. Eval chạy input qua nhiều model / nhiều prompt version, lấy output thật rồi so với expected để ra điểm — và so sánh các phiên bản. Khi đạt ngưỡng & review OK, prompt được promote lên Production (có thể chạy A/B testing).

⮕ Đầu vào bắt buộc của eval (đến từ ngoài — eval KHÔNG tự sinh)

  1. Production prompt — prompt đang cần đánh giá (cái "dưới kính hiển vi"). Được lưu thành Prompt version của suite trong Postgres (prompt_versions table). Suite luôn có 1 version được đánh dấu active thông qua con trỏ suites.active_prompt_version_id.
  2. route_context_json — input mô tả 1 route: route + entities(fields) + method_access(read/write) + call_chain. Do Code Analysis project sinh ra (phân tích AST/graph từ source Java, hàm _build_route_context()). Được nạp thành input của Case.

Eval chỉ tiêu thụ 2 thứ này — chất lượng route_context_json (có đủ entities + method_access hay không) quyết định oracle/eval có grounded hay phải đoán.

Cơ chế chấm điểm — "chấm điểm + ngưỡng + so khớp mềm"

Ba khái niệm này thay thế assertEquals của unit test. Lý do cần cả ba: LLM output không bao giờ "giống hệt" expected về mặt ký tự, nhưng có thể đúng về bản chất — cần đo theo bản chất, không đo theo chuỗi.

1 — Chấm điểm (Scoring)

Điểm số thay vì pass/fail nhị phân

Unit test: đúng hết = PASS, sai 1 chỗ = FAIL. Nhưng "đúng 5/6 cell CRUD" là kết quả rất tốt — bỏ đi uổng nếu dùng pass/fail. Scorer tính một điểm số 0.0–1.0:

score = matched_cells / total_cells
# vd: 5/6 = 0.833
2 — Ngưỡng (Threshold)

"Đủ tốt" thay vì "hoàn hảo"

Có điểm rồi, cần quyết định bao nhiêu thì "đạt". Ngưỡng được đặt trong suite config (không bắt buộc 1.0 vì LLM đôi khi đúng bản chất nhưng diễn đạt hơi khác):

threshold = 0.8
passed = score >= threshold
# 0.833 >= 0.8 → PASS
3 — So khớp mềm (Soft matching)

Chuẩn hoá trước khi so — không cần giống từng ký tự

Unit test: "Order::customerId" != "order::customer_id" → FAIL. Nhưng hai cái đó có nghĩa giống nhau. Hàm normalize_flat_ops chuẩn hoá cả hai phía trước khi compare:

# 1. camelCase → snake_case + lowercase
"Order::customerId" → "order::customer_id"  ✓

# 2. sắp xếp op alphabet
"RC" → "CR"  ✓  (giống "CR")

⮕ Ví dụ đầy đủ — 3 bước kết hợp

Expected (golden): Order.status=U, Order.totalPrice=U, Order.id=R

Model trả về: Order.status=U, Order.totalPrice=U, Order.Id=R (viết hoa I)

Bước 1 — normalize:  "Order.Id"  →  "order.id"  ✓ khớp với "Order.id"
Bước 2 — score:      3/3 = 1.0
Bước 3 — threshold:  1.0 >= 0.8  →  PASS

Nếu dùng assertEquals: "Order.Id" != "Order.id" → FAIL — sai, dù thực ra đúng.

Expected có thể ở 3 dạng — scorer CRUDOpsMatch xử lý cả 3 trước khi normalize:

  • Flat: {"Order::status": "U"}
  • List: {"cells": [{"entity":"Order","column":"status","op":"U"}]}
  • Nested (dạng fixture giàu metadata): {"cells": {"Order": {"status": {"op":"U","confidence":"high","oracle_why":"…"}}}}

6 bước Oracle Review lifecycle

  1. Meta-generate (optional) — production prompt → oracle prompt. Một "meta-prompt" biến production prompt thành oracle prompt chuyên sinh ground truth (thêm persona "senior JPA expert", chain-of-thought). Người có thể chỉnh tay trước khi chạy. API: POST /oracle-review/meta-generate.
  2. Generate fixture — model mạnh sinh expectation. Dùng model oracle (vd Opus) chạy oracle prompt trên input → ra các cell op + confidence + why. Lưu <id>.json (fixture) và <id>.review.json (chỉ cell cần review: confidence low/medium). API: POST /oracle-review/generate.
  3. Execute/Refine (optional, stateless) — thử oracle prompt. Chạy thêm lần nữa với oracle prompt khác để so sánh output trước khi chốt. Không ghi đè fixture — lịch sử run được lưu riêng. API: POST /oracle-review/run-with-prompt.
  4. Review & Approve — fixture là đơn vị duyệt. Người nhìn bảng entity/field/op: cell high có thể phớt lờ, tập trung soi cell low/medium — Approve (tin → confidence = high) / Fix (sửa op) / Remove (xoá cell). Khi gắn reviewed_by → reviewed_at được stamp → fixture chuyển trạng thái "approved". API: POST /oracle-review/{id}/review.
  5. Promote to suite → trở thành test_case. Flatten cells → insert vào test_cases DB (hoặc file .yml nếu file-backed). Metadata source_fixture lưu truy xuất nguồn gốc. API: POST /oracle-review/{id}/promote-to-suite.
  6. Case tham gia eval bình thường. Test case đã promote được dùng trong run thông thường (luồng §3 ở trên).

Vì sao "confidence" + "why" quan trọng khi review

Oracle tự chấm độ tin cậy mỗi cell và kèm lý do. Reviewer nhờ đó chỉ cần soi kỹ cái mơ hồ (low/medium), tin tưởng cái rõ ràng (high) → review nhanh, đỡ mệt, ít miss. Đây chính là cách biến việc "tạo golden cho từng field" từ thủ công & dễ sai thành duyệt có hỗ trợ.

Prompt version lifecycle

Một prompt version có 2 chiều độc lập:

  • Status (draft → staging → archived): vòng đời của version, do người thao tác.
  • Active pointer (suites.active_prompt_version_id): con trỏ suite trỏ vào version nào đang live. Promote = cập nhật con trỏ này, không thay đổi status của version cũ.

⚠ "Promoted" ≠ "status=staging". Một version status=staging vẫn có thể là active (live). Active pointer và status là 2 trục tách biệt.

Suite

Bộ đề thi

Nhóm bài test cho cùng loại bài toán (vd "CRUD Matrix"). Sở hữu nhiều Case, nhiều Prompt version (1 cái đang active) và lịch sử Run.

Case

1 câu hỏi + đáp án

Một test đơn lẻ = input + expected (+ scoring riêng nếu cần). Vd: input = GET /timesheets/:id, expected = MonthlyTimesheet mọi field = R.

Golden Set

Bảng đáp án chuẩn

Tập expected đã được người duyệt — "chân lý" để chấm. Tạo qua Oracle Review: oracle sinh → human approve → promote → test_case trong DB.

F File format — Fixture & Review JSON

Fixture — artifacts/eval/oracle_fixtures/<domain>/<id>.json

Mỗi fixture là 1 file JSON lưu đầy đủ audit trail. Khi reviewed_by rỗng → trạng thái "pending" (chưa duyệt).

{
  "fixture_id": "case1_happy_path",
  "suite_id": "crud_matrix_llm",
  "prompt_version": "crud_matrix_oracle.v1",
  "oracle_model": "claude-opus-4-8",
  "reviewed_by": "",          // rỗng = chưa approve
  "reviewed_at": "",          // ISO date khi finalize
  "input_data": { /* route_context_json — route + entities + method_access */ },
  "expected": {
    "cells": {
      "Order": {
        "status": { "op": "C", "confidence": "high", "oracle_why": "service.setStatus → write" },
        "id":     { "op": "",  "confidence": "medium", "oracle_why": "@GeneratedValue → DB assigns" }
      }
    },
    "valid_fields": { "Order": ["id", "status"] },
    "framework": "java_spring"
  },
  // Studio audit trail (chỉ có khi sinh qua UI):
  "production_prompt": "…",       // prompt đang được eval
  "oracle_prompt": "…",           // YAML prompt sinh ground truth
  "oracle_prompt_version": "…",
  "meta_prompt_version": "…"
}

Companion review — <id>.review.json

Chỉ chứa các cell cần người quyết định (confidence ∈ low/medium):

{
  "fixture_id": "case1_happy_path",
  "generated_at": "2026-05-26",
  "needs_review": [
    {
      "entity": "Order", "field": "id", "op": "", "confidence": "medium",
      "oracle_why": "@GeneratedValue → DB assigns id, app never writes it",
      "action": "remove",      // null=chưa quyết · approve · fix · remove
      "corrected_op": null     // set khi action="fix"
    }
  ]
}

Semantics của action khi approve:

  • approve → set confidence = high
  • fix → set op = corrected_op, confidence = high
  • remove → xoá cell khỏi fixture

Finalize (gắn reviewed_by) stamp reviewed_at=today() lên cả fixture → đây là thứ lật trạng thái từ "pending" sang "approved".

I Oracle input contract — route_context_json

Oracle prompt được template bằng {{ route_context_json }}. Khi input đúng chuẩn, oracle không đoán — mọi thứ được grounded từ input:

  • entities[].fields[].{name, db_column} → ground field names + casing (hàm _extract_valid_fields đọc chính xác field này, ưu tiên db_column)
  • method_access[].{read, write} → ground op trực tiếp: field trong read → R, trong write → C/U
{
  "route":       { "endpoint": "/api/orders/{id}", "http_method": "PUT",
                   "use_case": "Update order status", "action": "update" },
  "call_chain":  [ { "class": "OrderService", "method": "update", "method_key": "…" } ],
  "entities":    [ { "short_name": "Order", "fqn": "…", "db_table": "orders",
                     "annotations": ["@Entity","@Table(…)"],
                     "fields": [ { "name": "totalPrice", "db_column": "total_price",
                                   "annotations": ["@Column"] } ] } ],
  "method_access": [ { "class": "OrderService", "method": "update",
                        "read":  ["id","status"],        // → op R
                        "write": ["status","totalPrice"], // → op C/U
                        "annotations": ["@Transactional"] } ]
}

⚠ Fixture-shape caveat — non-conformant fixtures

Một số fixture cũ (vd studio_test_post_orders.json) có shape khác: {project_id, total, contexts: {"<route>": {call_edges, call_classes, step_actions, route}}} — không có entities và method_access. Với các fixture này, oracle phải đoán field từ call chain → reviewer phải soi kỹ hơn.

Đừng hand-author block entities giả để vá — hãy regenerate fixture từ route_context_json đúng chuẩn.

D Key Design Decisions

Protocols in core, impls in storage

App code phụ thuộc vào ISuiteStore, IPromptStore… — blast radius nhỏ khi swap Postgres ↔ memory/sqlite. Wiring duy nhất ở dev_server.py.

DB-only suites

Suite/case/run chỉ đọc từ Postgres, không có file fallback → loại bỏ file-vs-DB ambiguity. Oracle fixture vẫn là file cho đến khi promote.

Active pointer ≠ status

Promote → cập nhật suites.active_prompt_version_id. Status (draft/staging/archived) là vòng đời độc lập. Một version staging vẫn có thể là live.

Run resolves active prompt

POST /run không cần truyền prompt — tự resolve get_active(suite).config qua _system_prompt_from_config. Promote → lần run tiếp theo dùng version mới ngay.

Per-case scoring

Case's scoring JSONB drive build_scorers() qua EvalRunner.scorer_for. Fallback về suite-level scorers khi case không có spec riêng.

Casing-insensitive CRUD compare

normalize_flat_ops collapse camelCase/snake_case và op order — chỉ genuine op difference mới fail một cell. Áp dụng nhất quán trong cả scorer lẫn target trace.

Fixture là file, case là DB row

Fixture (chưa duyệt) → file JSON dễ edit/xoá/version. Sau khi promote → test_cases row trong DB, tham gia eval bình thường. Hai giai đoạn, hai storage khác nhau.

Oracle prompt tách khỏi production prompt

Oracle prompt (sinh ground truth) lưu YAML file trong eval_consumer/.../prompts/. Production prompt (đang được eval) lưu trong prompt_versions DB. Hai mục đích, hai nơi.
