1 文で要約すると: 従来のソフトウェアでは出力が固定なので ユニット/ITテスト で十分だったが、 LLM の出力は毎回変わるため == でアサートできない — eval（評価基準に基づく採点） が必要になる。 eval には各ケースの 期待値（expected） が要る。大規模コードベースで人手で作るのは非現実的なため、 ゴールデンデータセット フェーズで強力な LLM が期待値を生成し、人間は レビューするだけ → プロモート して eval が使う fixture になる。

W WHY — なぜ評価フレームワークが必要か

従来のソフトウェア: ユニットテスト / IT で十分

通常のコードは 決定論的（deterministic）: 同じ入力 → 常に同じ出力。 だから assertEquals(expected, actual) だけでテストできる。合否が明確。

LLM: 出力が変わる → == アサートが無意味

同じ入力でも、LLM は温度・サンプリング・モデル変更・プロンプト変更により毎回異なる出力を返す。 完全一致では比較できない。柔軟な基準 で採点する必要がある: 構造が正しいか・必要な情報を含むか・類似度が閾値を超えるか・CRUD op が正しいか… — これが eval の役割。

観点従来のソフトウェアLLM アプリケーション
出力決定論的、正解は 1 つ変動する、正しい表現が複数ある
テスト方法ユニットテスト / IT: == expectedeval: 採点 + 閾値 + ソフトマッチング
モデル/プロンプト変更時ロジックは変わらない結果が変わる → 測定・バージョン比較が必要
「正解」(expected) の作成開発者が少量を手書き大量 & 手作りが困難 → ゴールデンデータセットが必要

大規模コードベースの文脈

何百ものルート / エンティティ / フィールドに対して フィールドごとに「正解」を手作業で作る のは非現実的: 人間は 見落とし、疲労、ミス、一貫性の欠如が生じる。 コードを 1 行ずつ読んでゴールデンデータセットを手動で構築することはできない。

「本番環境で動かして結果を見る」ではダメなのか

本番で確認するのは遅く、リスクが高い。また、複数モデル / 複数プロンプトバージョンを 公平に同時比較 できない。eval は オフライン で高速に反復でき、リリース前に A/B 比較が可能。

5 5W2H — 全体像を一覧で

What

何か

テストケース（入力 + 期待値） のセットをモデル/プロンプトで実行し、採点 して比較するシステム。 System → Domain → Suite → Case / Prompt version / Run で構成される。

Why

なぜ

LLM 出力が変動する → ユニットテストでは不十分。品質を測定し、モデル / プロンプトバージョンを比較する必要がある。

Who

誰が

開発者 / プロンプトエンジニアが eval を実行。レビュアー（人間） が Oracle Review UI でゴールデンデータセットを承認。

When

いつ

プロンプト/モデル変更前、回帰チェック、バージョン比較時 — 本番環境を待たずに 実施。

Where

どこで

Ryuu Eval: Suite → Case → Prompt version → Run。期待値は Oracle Review で生成。 Fixture はファイル保存、Case/Run は Postgres 保存。

How

どのように

Oracle Review で期待値を生成（6 ステップ）→ 人間がレビュー → DB の test_case にプロモート → Run が Scorer で採点。

How much

コスト

重い部分（期待値生成）は強力な LLM が自動化。人間は low/medium confidence のセルだけ レビュー → 工数削減・ミス低減。

H HOW — 評価フロー（採点）

各ケースには 入力 と 期待値 がある。eval は入力を複数のモデル / プロンプトバージョンで実行し、 実際の出力を期待値と比較してスコアを算出 — バージョン間を 比較 する。 閾値達成 & レビュー OK になったらプロンプトを 本番環境にプロモート（A/B テストも可能）。

⮕ eval に必須の入力（外部から来る — eval 自身は生成しない）

  1. 本番プロンプト（Production prompt） — 評価対象のプロンプト（「顕微鏡下」のもの）。 Suite の Prompt version として Postgres (prompt_versions テーブル) に保存される。 Suite は常に 1 つのバージョンを active としてポインタ suites.active_prompt_version_id で管理。
  2. route_context_json — 1 ルートを記述する入力: route + entities（フィールド） + method_access（read/write） + call_chain。 Code Analysis プロジェクト が Java ソースの AST/グラフ解析で生成 （_build_route_context()）。Case の input として格納。

eval はこの 2 つを 消費するだけ — route_context_json の品質 （entities + method_access が揃っているか）が oracle/eval のグラウンディングを左右する。

採点の仕組み — 「スコアリング + 閾値 + ソフトマッチング」

この 3 つは assertEquals の代替。LLM 出力は文字列として「完全一致」することはないが、 意味的には正しい 場合がある — 文字列ではなく意味で測定する必要がある。

1 — スコアリング (Scoring)

合否の 2 値判定ではなくスコアで評価

ユニットテスト: 全部正解 = PASS、1 箇所ミス = FAIL。しかし「6 セル中 5 セル正解」は 非常に良い結果 — 2 値判定では FAIL になってしまい、もったいない。Scorer は 0.0〜1.0 のスコアを算出:

score = matched_cells / total_cells
# 例: 5/6 = 0.833
2 — 閾値 (Threshold)

「完璧」ではなく「十分に良い」で判定

スコアが出たら「何点以上で合格か」を決める必要がある。閾値は Suite の設定で指定 （LLM は意味的に正しくても表現が微妙に異なる場合があるため 1.0 は要求しない）:

threshold = 0.8
passed = score >= threshold
# 0.833 >= 0.8 → PASS
3 — ソフトマッチング (Soft matching)

文字単位ではなく正規化してから比較

ユニットテスト: "Order::customerId" != "order::customer_id" → FAIL。 しかし両者は同じ意味。normalize_flat_ops は比較前に両側を正規化する:

# 1. camelCase → snake_case + 小文字化
"Order::customerId" → "order::customer_id"  ✓

# 2. op をアルファベット順にソート
"RC" → "CR"  ✓  ("CR" と一致)

⮕ 完全な例 — 3 ステップを組み合わせる

期待値（ゴールデン）: Order.status=U, Order.totalPrice=U, Order.id=R

モデルの出力: Order.status=U, Order.totalPrice=U, Order.Id=R（I が大文字）

ステップ 1 — 正規化:  "Order.Id"  →  "order.id"  ✓ "Order.id" と一致
ステップ 2 — スコア:  3/3 = 1.0
ステップ 3 — 閾値:    1.0 >= 0.8  →  PASS

assertEquals なら: "Order.Id" != "Order.id" → FAIL — 実際には正解なのに。

期待値は 3 つの形式を受け付ける — CRUDOpsMatch は正規化前にすべてを処理する:

  • フラット: {"Order::status": "U"}
  • リスト: {"cells": [{"entity":"Order","column":"status","op":"U"}]}
  • ネスト形式（メタデータ付き fixture）: {"cells": {"Order": {"status": {"op":"U","confidence":"high","oracle_why":"…"}}}}

Oracle Review ライフサイクル — 6 ステップ

  1. メタ生成（任意）— 本番プロンプト → oracle プロンプト。 「メタプロンプト」が本番プロンプトを oracle プロンプト（グラウンドトゥルースを生成する専用プロンプト）に変換する （「シニア JPA エキスパート」ペルソナ、chain-of-thought を追加）。実行前に人間が編集可能。 API: POST /oracle-review/meta-generate
  2. Fixture 生成 — 強力なモデルが期待値を生成。 oracle モデル（例: Opus）が oracle プロンプトを入力で実行 → 各セルの op + confidence + why を出力。<id>.json（fixture）と <id>.review.json（レビュー要: confidence が low/medium のセルのみ）を保存。 API: POST /oracle-review/generate
  3. 実行/精緻化（任意・ステートレス）— oracle プロンプトを試す。 別の oracle プロンプトで追加実行して出力を比較し、確定前に検証できる。 Fixture を上書きしない — 実行履歴は別途保存。 API: POST /oracle-review/run-with-prompt
  4. レビュー & 承認 — fixture が承認の単位。 人間がテーブル（entity / field / op / confidence）を確認: high セルはスキップ可、 low/medium セルに集中して Approve（信頼 → confidence = high）/ Fix（op を修正）/ Remove（セルを削除）。 reviewed_by を設定すると reviewed_at がスタンプされ → fixture が「approved」に変わる。 API: POST /oracle-review/{id}/review
  5. Suite にプロモート → test_case になる。 セルをフラット化 → test_cases DB に insert（またはファイルバックの場合は .yml ファイル）。 メタデータ source_fixture でトレーサビリティを確保。 API: POST /oracle-review/{id}/promote-to-suite
  6. ケースが通常の eval に参加。 プロモートされた test_case が通常の Run で使用される（ステップ 3 の評価フロー参照）。

なぜ "confidence" と "why" がレビューで重要か

Oracle は各セルの信頼度と理由を自己評価する。レビュアーはこれにより 曖昧なものだけを精査 （low/medium）し、明確なもの（high）は信頼できる → レビューが速く、疲労が少なく、見落としが少ない。 これがフィールドごとの「ゴールデン作成」を 手作業で誤りが多い作業 から 支援付きレビュー に変える仕組み。

Prompt version のライフサイクル

Prompt version には独立した 2 つの軸がある:

  • ステータス（draft → staging → archived）: バージョンのライフサイクル。人間が操作する。
  • Active ポインタ（suites.active_prompt_version_id）: Suite がどのバージョンをライブとして指すか。 プロモート = このポインタを更新するだけ。古いバージョンのステータスは 変わらない。

⚠ "Promoted" ≠ "status=staging"。staging ステータスのバージョンが active（ライブ）になりえる。 Active ポインタとステータスは完全に独立した 2 軸。

Suite

テストセット

同種の問題をまとめたテストグループ（例: "CRUD Matrix"）。複数の Case、 複数の Prompt version（1 つが active）、Run 履歴を所有する。

Case

1 問 + 正解

単一のテスト = input + expected（+ 必要なら scoring も個別指定）。 例: 入力 = GET /timesheets/:id、期待値 = MonthlyTimesheet の全フィールド = R。

Golden Set

標準正解セット

人間が承認した expected の集合 — 採点の「真実」。Oracle Review で作成: oracle 生成 → 人間承認 → プロモート → DB の test_case。

F ファイルフォーマット — Fixture & Review JSON

Fixture — artifacts/eval/oracle_fixtures/<domain>/<id>.json

各 fixture は完全な監査証跡を持つ JSON ファイル。reviewed_by が空 → 「pending」（未承認）状態。

{
  "fixture_id": "case1_happy_path",
  "suite_id": "crud_matrix_llm",
  "prompt_version": "crud_matrix_oracle.v1",
  "oracle_model": "claude-opus-4-8",
  "reviewed_by": "",          // 空 = 未承認
  "reviewed_at": "",          // 確定時の ISO 日付
  "input_data": { /* route_context_json — route + entities + method_access */ },
  "expected": {
    "cells": {
      "Order": {
        "status": { "op": "C", "confidence": "high", "oracle_why": "service.setStatus → 書き込み" },
        "id":     { "op": "",  "confidence": "medium", "oracle_why": "@GeneratedValue → DB が割り当て" }
      }
    },
    "valid_fields": { "Order": ["id", "status"] },
    "framework": "java_spring"
  },
  // Studio 監査証跡（UI 経由で生成した場合のみ）:
  "production_prompt": "…",       // 評価対象のプロンプト
  "oracle_prompt": "…",           // グラウンドトゥルース生成用の YAML プロンプト
  "oracle_prompt_version": "…",
  "meta_prompt_version": "…"
}

Companion review — <id>.review.json

人間の判断が必要なセルのみ（confidence ∈ low/medium）を格納:

{
  "fixture_id": "case1_happy_path",
  "generated_at": "2026-05-26",
  "needs_review": [
    {
      "entity": "Order", "field": "id", "op": "", "confidence": "medium",
      "oracle_why": "@GeneratedValue → DB が id を割り当て、アプリは書き込まない",
      "action": "remove",      // null=未決定 · approve · fix · remove
      "corrected_op": null     // action="fix" の場合に設定
    }
  ]
}

承認時の action のセマンティクス:

  • approve → confidence を high に設定
  • fix → op = corrected_op に設定、confidence を high に設定
  • remove → fixture からセルを削除

確定（reviewed_by を設定）すると fixture 全体に reviewed_at=today() がスタンプされる → これが「pending」から「approved」への状態遷移のトリガー。

I Oracle 入力コントラクト — route_context_json

Oracle プロンプトは {{ route_context_json }} でテンプレート化される。 入力が正しい形式なら oracle は 推測しない — すべてが入力からグラウンディングされる:

  • entities[].fields[].{name, db_column} → フィールド名とケーシングをグラウンディング （_extract_valid_fields がこのフィールドを読み取り、db_column を優先）
  • method_access[].{read, write} → op を直接グラウンディング: read のフィールド → R、write のフィールド → C/U
{
  "route":       { "endpoint": "/api/orders/{id}", "http_method": "PUT",
                   "use_case": "注文ステータス更新", "action": "update" },
  "call_chain":  [ { "class": "OrderService", "method": "update", "method_key": "…" } ],
  "entities":    [ { "short_name": "Order", "fqn": "…", "db_table": "orders",
                     "annotations": ["@Entity","@Table(…)"],
                     "fields": [ { "name": "totalPrice", "db_column": "total_price",
                                   "annotations": ["@Column"] } ] } ],
  "method_access": [ { "class": "OrderService", "method": "update",
                        "read":  ["id","status"],        // → op R
                        "write": ["status","totalPrice"], // → op C/U
                        "annotations": ["@Transactional"] } ]
}

⚠ Fixture shape の注意 — 非準拠 fixture

一部の古い fixture（例: studio_test_post_orders.json）は異なる形式: {project_id, total, contexts: {"<route>": {call_edges, call_classes, step_actions, route}}} — entities も method_access もない。 この場合、oracle はコールチェーンからフィールドを推測するため、レビュアーはより注意深く確認が必要。

偽の entities ブロックを手作りして誤魔化さないこと — 正しい route_context_json から fixture を再生成する こと。

D 主要設計判断

プロトコルは core に、実装は storage に

アプリコードは ISuiteStore、IPromptStore などのプロトコルに依存 — Postgres ↔ memory/sqlite の差し替えは dev_server.py の 1 箇所だけ変更すれば良い。

Suite は DB 専用

Suite/Case/Run は Postgres のみ — ファイル vs DB の曖昧さを排除。Oracle fixture はプロモートまでファイルのまま。

Active ポインタ ≠ ステータス

プロモート → suites.active_prompt_version_id を更新。ステータス（draft/staging/archived）は独立したライフサイクル。staging のバージョンがライブになりえる。

Run が active プロンプトを解決

POST /run でプロンプトを明示しなくても get_active(suite).config を _system_prompt_from_config で自動解決。プロモート → 次回 Run から新バージョンを使用。

ケースごとの採点

ケースの scoring JSONB が build_scorers() を駆動 (EvalRunner.scorer_for 経由)。ケースに個別 spec がなければ Suite レベルのスコアラーにフォールバック。

大文字小文字を無視した CRUD 比較

normalize_flat_ops が camelCase/snake_case と op の順序を統一 — 本質的な op の差異だけがセルを失敗させる。スコアラーと target の両方で一貫して適用。

Fixture はファイル、Case は DB 行

未承認の Fixture → 編集/削除/バージョン管理が容易な JSON ファイル。プロモート後 → DB の test_cases 行として通常の eval に参加。2 フェーズ、2 つのストレージ。

Oracle プロンプトと本番プロンプトを分離

Oracle プロンプト（グラウンドトゥルース生成用）は eval_consumer/.../prompts/ の YAML。本番プロンプト（eval 対象）は prompt_versions DB。目的が異なるため保存場所も分ける。
